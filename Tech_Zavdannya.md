# Технічне завдання — Система обліку видачі та повернення книг у бібліотеці

## 1\. Загальні відомості

|Поле|Значення|
|-|-|
|Назва проєкту|Система обліку видачі та повернення книг|
|Тип ПЗ|Вебзастосунок (SPA + REST API)|
|Замовник|Бібліотека навчального закладу|
|Цільова аудиторія|Бібліотекарі, читачі|
|Документ|Технічне завдання, v1.0|



## 2\. Призначення та мета системи

**Призначення:** автоматизація обліку бібліотечного фонду — реєстрація книг, видача читачам, контроль повернення та строків.

**Мета:**

* замінити паперовий журнал обліку електронною системою;
* зменшити кількість неповернутих книг через автоматичний контроль прострочень;
* дати читачу прозорий доступ до каталогу та власної історії видач;
* скоротити час оформлення видачі до ≤ 60 секунд.



## 3\. Ролі користувачів

* **Бібліотекар (адміністратор)** — керує каталогом книг, оформлює видачу/повернення, керує обліковими записами читачів, бачить список боржників.
* **Читач** — переглядає каталог, свою історію видач та поточні книги на руках.
* **Планувальник (системний актор)** — щоденно автоматично перевіряє прострочення та оновлює статуси.



## 4\. Основний функціона

1. Облік книг — додавання, редагування, видалення (назва, автор, рік, ISBN, кількість екземплярів).
2. Реєстрація читачів з автоматичною генерацією унікального номера читацького квитка.
3. Оформлення видачі з датою видачі та плановою датою повернення (+14 днів).
4. Відмітка про повернення з автоматичним обчисленням днів прострочення.
5. Автоматичне формування списку боржників (щоденне оновлення).
6. Пошук книг за назвою/автором та перегляд історії видач читача.
7. Блокування видачі за наявності прострочень або 5 книг на руках.

## 6\. Модель життєвого циклу

**Обрана модель: Ітеративно-інкрементна (Iterative-Incremental).**

**Обґрунтування:**

* Функціонал системи природно ділиться на незалежні блоки (каталог → видача → контроль прострочень → звіти).
* Вимоги з MoSCoW-пріоритизацією самі диктують порядок: спочатку Must, потім Should, потім Could.
* Можна отримати працюючий MVP уже після 1-ї ітерації та показати бібліотекарю для feedback.
* Waterfall не підходить — заборонено повертатись до попередніх етапів при уточненні вимог.
* Спіральна модель — надлишкова для проєкту без високих ризиків.

**Короткий опис інкрементів:**

|№|Інкремент|Вимоги|Тривалість|
|-|-|-|-|
|1|MVP: автентифікація, каталог книг, реєстрація читачів|FR-01, FR-02, NFR-02|2 тижні|
|2|Оформлення видачі та повернення|FR-03, FR-04|1 тиждень|
|3|Автоматичний контроль прострочень, список боржників|FR-05, NFR-03|1 тиждень|
|4|Пошук, фільтрація, кабінет читача, оптимізація|NFR-01, NFR-04|1 тиждень|
|5|Документація API, тестування, рефакторинг|NFR-05|1 тиждень|



## 7\. Етапи розробки (SDLC)

1. **Аналіз вимог** — SRS, user stories, use case diagram *(виконано, лаб. №2)*.
2. **Проєктування** — архітектура, схема колекцій MongoDB, API-контракти (OpenAPI).
3. **Реалізація** — за інкрементами з п. 6.
4. **Тестування** — unit, integration, E2E (покриття бізнес-логіки ≥ 70 %).
5. **Впровадження** — деплой на хостинг, навчання бібліотекаря.
6. **Супровід** — виправлення багів, бекапи, оновлення.



## 8\. Критерії приймання

Проєкт вважається готовим, коли:

* усі вимоги з пріоритетом **Must** (FR-01…FR-05, NFR-01, NFR-02) реалізовані та покриті тестами;
* вимоги **Should** (NFR-03, NFR-04) реалізовані або мають план впровадження;
* усі 6 user stories (US-01…US-06) мають виконані acceptance criteria;
* час оформлення видачі книги ≤ 60 секунд (NFR-04 підтверджено на тестах);
* час відповіді пошуку ≤ 2 секунд при 10 000 книг (NFR-01 підтверджено навантажувальним тестом);
* система розгорнута на тестовому середовищі та доступна за публічним URL;
* README.md і документація в `/requirements` оновлені.



## 9\. Обмеження

* Проєкт реалізується силами навчальної команди (без зовнішнього фінансування).
* Хостинг — безкоштовний рівень (Render / Railway / Vercel + MongoDB Atlas Free).
* Інтерфейс лише українською мовою.
* Браузери: Chrome, Firefox, Safari; екрани від 360 px.
* Node.js виключно LTS-версії.
